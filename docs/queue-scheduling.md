# 单卡队列与并发测速

Web 和 PHP API 的 Lite、Pro、Max 任务使用同一个 SQLite 队列。每次启动一个任务，调度器都会重新检查指定 GPU 的空闲显存、主机可用内存、可用 CPU 核心和任务盘空间。具备余量时，不同任务在独立进程组中同时运行。

## 启动与校准

启动入口为 `php php/bin/worker.php`。同一 `SUBTITLE_DATA_DIR` 只运行一个调度器。默认最多并行 3 个任务。运行中的任务另有独立的进程和文件锁，调度器意外退出后，重新启动相同入口即可接管。

在空闲的测试队列中放入一批任务后，下面的命令处理到队列为空即退出。比较并发时，分别使用新任务和同一批输入，避免复用已生成的修复阶段。每个送入模型的测试视频最长 120 秒。[测试素材约定](../AGENTS.md)

```bash
SUBTITLE_MAX_JOBS=1 php php/bin/worker.php --drain
SUBTITLE_MAX_JOBS=3 php php/bin/worker.php --drain
```

`--max-jobs N` 可在命令行设置并发上限。`--once` 尝试处理一条任务，资源不足时保留排队状态并返回 75。GPU 默认使用第 0 张，也可通过 `CUDA_VISIBLE_DEVICES` 指定。调度器查询第一张可见卡，并把这张卡的 UUID 传给获准启动的推理进程。GPU 探测失败时，需要显存的任务继续等待。手动设置 `LITE_DEVICE=cpu` 的 Lite 任务可以使用 CPU 推理。

在部署环境中用 `SUBTITLE_SCHEDULER_CONFIG` 指向 JSON 文件，重启调度器后生效。下表列出初始估算。完成目标显卡和代表视频的单任务测试后，可根据实测峰值调整对应参数。

| 模型阶段 | 预留显存 MiB | 基础内存 MiB | CPU 核心 | 基础临时空间 MiB |
| --- | ---: | ---: | ---: | ---: |
| `lite`，GPU OCR 和 LaMa，720p 基础值 | 4096 | 3072 | 4 | 512 |
| `clear`，字幕 | 20480 | 12288 | 4 | 1024 |
| `propainter`，水印 | 22528 | 8192 | 4 | 1536 |
| 系统保留余量 `headroom` | 1536 | 2048 | 1 | 2048 |

新版 Lite 按输入像素数增加预留。720p 的基础显存为 4 GiB，1080p 起为 8 GiB。主机内存从 3 GiB 起随像素数增加，另计解码帧。1620×2880 的街访实测进程显存峰值约 6.58 GiB、主机内存约 6.26 GiB。自定义 `profiles.lite` 中的显存或主机内存数值可覆盖对应的自动增量。

混合任务按各阶段所需资源的最大值预留，并按画面尺寸加入解码缓存，按源片体积和中间副本数量增加磁盘预算。混合流程还按帧数和画面尺寸估算无损中间片。调度器从当前系统余量中扣除运行任务尚未用到的预留量，因此其他服务已经占用的显存、内存和磁盘也会影响能否开工。Linux 读取 CPU 亲和性和 cgroup 配额，并给同时运行的任务分配 CPU 核心。

以下配置只覆盖列出的值。资源名称为 `gpu_mib`、`ram_mib`、`cpu_cores` 和 `disk_mib`。建议先用同一批片段取得实时数据，再修改资源预留量。

```json
{
  "max_jobs": 2,
  "poll_seconds": 1,
  "max_bypasses": 3,
  "profiles": {
    "lite": {"cpu_cores": 3}
  },
  "headroom": {"gpu_mib": 2048}
}
```

队列按入队时间检查。较早的任务暂时缺少资源时，可先放行能装下的较小任务。默认允许 3 次，之后暂停放行后来的任务，等待资源回到可用状态。估算已经超过机器物理容量的任务会显示等待资源，并允许其他可运行任务继续。运行中的普通任务并发遇到内存耗尽时，调度器保留原参数和已完成的修复阶段，等其他任务退出后独占重试一次。独占重试失败后，接口显示失败原因。普通失败仅结束该任务。工作进程组意外退出后，该任务会标记为中断，可以从原接口重试。

## 核对运行证据

SQLite 的 `job_runs` 为每次尝试单独记录 `job_id`、`run_id`、`queued_at`、`started_at`、`finished_at`、`outcome`、`reservation_json`、`exclusive` 和 `overlapped`。时间为 Unix 秒，可含小数。两条记录满足 `max(started_at) < min(finished_at)` 即存在任务级重叠。具体模型调用是否重叠，可再核对每个任务目录下 `runs/<run_id>/` 的记录。

| 文件 | 记录及口径 |
| --- | --- |
| `stage_starts.jsonl` | 工作进程刚进入的实际操作。进程在推理中被强制终止时，也可查看最后开始的操作。 |
| `stages.jsonl` | 已经返回的操作，含阶段名、执行进程、起止时间和成功标志。通过 `span_id` 匹配开始记录。另有 `queue_wait` 记录入队到放行的时间。 |
| `metrics.jsonl` | 设备总显存、当前空闲显存、整卡利用率、GPU 进程显存表，以及任务进程组的显存、RSS、CPU、进程 ID。包括主机剩余内存、CPU、磁盘和任务生成文件的占用。 |

`lite_ocr` 对应 CPU 检测调用，`lite_lama` 只在命中字框并调用 LaMa 时产生。`clear_inference` 记录实际模型调用，`phase` 区分首遍和精修。`propainter_inference` 对应实际交给 ProPainter 的窗口。`max_review` 是逐帧对照检查。`ffmpeg_encode` 记录编码进程的整个生命周期，期间也可能等待模型提供帧。`ffmpeg_finalize` 记录关闭输入、等待编码和封装结束的时间。同一任务的几个阶段可能重叠，计时请使用区间并集。

设备利用率包含显卡上的所有用户。任务显存通过 NVIDIA 进程表和任务进程组交叉归属。缺少进程明细或容器 PID 无法核对时，任务显存记录为 `null`，调度器继续保留相应的显存预算。已初始化 CUDA 的 PyTorch 调用还记录本进程分配器的保留显存和峰值。CPU 的 100% 表示用满一个核心。任务生成文件占用最多每 5 秒重新统计一次，上传原片与符号链接不计入。采样点之间的短时峰值可能被遗漏。

比较吞吐可用整批输入总时长除以首次入队到最后可下载的耗时，并同时保留每条任务的排队时间、处理时间和成片质量。调度器使用逐任务的内存预留，实测吞吐仍取决于模型、输入尺寸和同卡其他服务。

单卡 L20 的实测覆盖三条 Lite、轻重混合、三条 CLEAR 任务和长短混合。每组同时记录整批完成耗时、画质合格的原视频分钟数，以及各任务实际进入模型调用的时间区间。[L20 调度结果与任务时间线](l20-subtitle-benchmark-20261127.md#多视频并发)
