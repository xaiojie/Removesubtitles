# 单卡 L20 去字幕测试

原标准基线为 `b7f26f2` 的 CLEAR balanced，第一轮三档配置为 `53dd040`，加入深色场景彩色字幕处理后，独立验收冻结为 `46ba783`。Web 与 PHP API 从同一份档位表取参数，共用后台队列。实验机器有一张 NVIDIA L20（驱动报告 46,068 MiB），16 个逻辑 CPU，处理器为 Xeon E5-2686 v4，系统内存约 60 GiB，PyTorch 2.8.0+cu128。

单任务从启动独立处理进程计至成片编码封装、写入完成，涵盖加载、检测、模型推理和档位自带的复查。该对照使用机器默认的 CPU 亲和性。线上队列会给并发任务分配 CPU 核心，等待时间、任务耗时和真实 HTTP 下载另有记录。并发对照从调度器开始放行计至最后一个成片完成，上传用时单列。主集由 15 条短片组成，每条都会付一次启动成本，实际长视频耗时需要单独测量。

## 本轮选档结论

15 条原片共 60.475 秒。每条都独立启动一次任务，原标准合计 22 分 06 秒，Lite 合计 7 分 37 秒，新 Pro 合计 19 分 03 秒，Max 合计 21 分 22 秒。三项总耗时比例都达标。单条连续一分钟视频只付一次启动成本，镜头数、字幕出现时长和选区大小也会改变耗时。

**纯字幕批量处理优先选 Lite。** 15 条都擦除了能辨认的字幕，10 条通过完整画质检查，6 条独立验收中有 5 条合格。5 个问题样片为 c06 动画粗描边、c11 双语黑底、c12 黄色刷底、c13 紫色半透明卡片和 c16 白色动画字卡。带底板的 5 条仅 c14（背景较简单，切镜后字幕消失）在三档都合格。

**Pro 保留默认入口，适合需要水印流程，或字幕盖住细线、装饰件时做对照。** c01 的项链、c10 的车内金属边线得到较好保留。15 条中 12 条文字擦净，5 条达到画质门槛。c03 留下单字形状，c04 黑边标题和 c05 屏幕录制文字仍可读，这三条的 Lite 成片均合格。

**Max 的改善集中在个别帧。** c13 第 44、60 帧的亮白残影减少，整条紫色底板仍明显。15 条中，Max 和 Pro 的 5 条合格样片完全相同。现有证据不足以把 Max 当作普遍画质更高的交付档。下一轮最值得单独验证的是持续跟踪字幕底板的边界，并在生成前保留能从邻帧直接找回的人物和道具轮廓。已经看过的独立验收片只用于回归，下一轮泛化评估需另留新片。

Web 批量添加的视频可以分别选档、指定多处字幕和水印，并分别查看进度和下载。两个入口都从同一份设置生成任务。Lite 使用 PP-OCRv5 Mobile 和 GPU LaMa。Pro 使用 5 步 CLEAR 与 LaMa 引导，水印交给 ProPainter。Max 使用 7 步 CLEAR、对齐邻帧的引导和水印复查。[服务使用的完整参数](../php/product_modes.json)

## L20 并发配置的选择

**纯 Lite 使用 3 个槽位。** 同批 3 段视频耗时从 100.49 秒降到 38.57 秒，缩短 61.6%。独立任务的 LaMa 调用有 6.89 秒三方重合，整卡峰值 3.39 GiB。进程表与调用区间交叉核对，27 个任务采样点同时看到了三个模型调用中的任务占有显存。这组 3 条输出只有 1 条画质合格，合格吞吐从 2.99 提高到 7.78 原视频分钟/小时。

**一重两轻可用 2 至 3 个槽位。** 逐个处理用时 140.01 秒，两并发 75.39 秒，三并发 75.85 秒。二者相差 0.47 秒，各做一轮不足以区分稳定的速度差。三并发实测有 3.96 秒三方模型调用重合。这台服务器的队列上限保留为 3，处理重任务时继续执行显存和 CPU 预留。

**常规 CLEAR 重任务同时放行两条。** 三条重任务逐个处理共 238.07 秒，允许两条同时运行后为 164.46 秒，缩短 30.9%。两条模型调用最长重合 44.68 秒。用默认预留把任务槽上限增至 3 后仍只出现两个重模型同时调用，耗时 162.35 秒。

同一组窄选区另把 CLEAR 单任务预留临时调到 14 GiB，三条重任务处理用时 153.33 秒，整卡采样峰值 26.31 GiB，三方实际模型调用重合 62.53 秒。对比默认两并发的 164.46 秒，差异为 6.8%（实验组更快）。本组 c06、c07、c03 的三份 CLEAR 输出都未通过画质验收。14 GiB 只在这组分辨率和选区做过校准，线上一般任务继续按 20 GiB 预留。

**长短混合可并行处理。** 20 秒 Lite 与 4 秒的字幕加水印 Pro，逐个处理 181.87 秒，两并发 123.64 秒，缩短 32.0%。两条模型调用重合 22.13 秒，两个任务之间 GPU 调用与 CPU 阶段的单向重合最长 13.96 秒。短片水印区与长片字幕区独立保存。两段来自同一原片，双入口联调另用三个不同来源。

这些重叠时间来自模型调用开始和返回、CPU 阶段与 NVIDIA 进程采样。任务分别持有自己的模型实例。GPU 内核级的同时执行时间需另做驱动分析。资源不足时按当前队列等待或独占重试，冻结批次内没有发生 OOM。

## 输入与复核

先查本机 Downloads，以抽帧确认字幕样式，成片与对比片独立索引。主测试集有 12 条本机原片和 3 条按底板样式补充的网络原片。普通字幕、粗体或粗描边、粗体或粗暗边加底板各 5 条，每类 3 条调参、2 条独立验收。单条 3.47～5 秒，合计 1,794 帧、约 60.475 秒。另有真实字幕加水印的 4 秒样片和用于长短混合调度的 20 秒样片。每次送入模型前校验片段摘要、选区和 120 秒上限。所有测试原片均经抽帧确认含字幕。两条留出样片附发布方的无字幕原片，只用来逐帧计算背景重建误差。[样片与来源](../benchmarks/corpus/README.md)

画质复核覆盖字幕切换、切镜、最后一秒和真实尾帧。并排对照原片和成片，检查可读残字、漏句、轮廓、底板、背景涂抹与闪烁。对每帧选区再做文字识别，筛出与原片位置重合、内容匹配的文字。OCR 匹配帧数是复核线索，读不到的残影、同框背景字和人物轮廓仍须从画面判断。配有干净参考的样片同时比较选区内平均绝对像素误差（MAE，0 至 255，越低越好）。

离线文字复核在本机使用 Apple Vision 的简体中文与英文准确识别，关闭自动语言纠正。对原片与成片同一显示帧的识别框比对，要求交集至少覆盖较小框的 25%，同时比较归一化后的字符串。只有实际图像通过复核才计入合格吞吐。独立样片 c04 的 Pro 输出在自动匹配中记录为零帧，但第 91 至 110 帧的“赢了多少次”仍可阅读，已按漏擦处理。

| PP-OCRv5 Mobile 与 GPU LaMa 的初始参数 | 26.35 秒 | 0 | 快速，遮挡的动画轮廓有软化 |
| CLEAR 直接 12 步 | 109.86 秒 | 0 | 消除了可读字幕，重新生成了部分被挡细节 |
| 标准后逐帧筛查、疑似字幕局部精修 | 144.12 秒 | 39 | 第二句仍有残字，局部精修耗时超过 12 步方案 |

Rank 48 实验将原适配器的 300 对 LoRA 矩阵乘积做截断 SVD，保存为独立权重。平均保留能量 98.84%，文件 SHA-256 为 `f2a575bf0e945b4755c558c773959652bbfb702396432fa5a8a6eed40f223520`。任务记录确认实际加载该文件。同一实验代码使用官方权重和原参数生成的首遍成片，与固定基线 c06 的 SHA-256 一致。冻结配置采用官方权重、强度 1.15。此次权重实验属于数值重构，未使用新数据训练。[独立权重生成脚本](../benchmarks/l20/make_lora_variant.py)

逐项可复现的调参表有 41 条实跑记录，包含采样间距 6/8 帧、字框外扩 5/9 像素、背景上下文 28/60 像素、LaMa 批大小 4/6，以及 CLEAR 的上下文、步数、分块和 LoRA 强度。每条记录附版本、输入摘要、实测显存和耗时。[逐次试验数据](../benchmarks/l20/results/20261127/tuning-runs.csv)

c12 的黄底粗字在早期 Lite 中能擦掉文字，留下完整黄色底条。增加彩色底板识别后，将底板覆盖范围合入遮罩。c16 的黑字白色字卡会遮挡麦克风，早期 CLEAR 仍留白边，调整遮罩边界后能看到麦克风，但局部轮廓仍有重建痕迹。c07 的游戏道路上，使用对齐的邻帧能补回部分地面纹理。试验比较了 4、5、7、8、12 步，以及区域、较大和全画面上下文。另以 25 帧分块测试了 c01，冻结配置保留 33 帧分块、4 帧重叠。

同模型、同参数、同一条 c06 在固定提示词向量冷缓存时耗时 95.64 秒，命中缓存时 91.28 秒，该编码阶段从 3.50 秒下降到不足 0.01 秒。两次均重新加载模型，其余 GPU 推理仍按视频独立执行。

在冻结版 Pro 的 c02 单任务里，加载 CLEAR 主模型用时 8.07 秒，加载适配器用时 2.01 秒。模型驻留后，第一块 CLEAR 推理用时 10.95 秒，第二块 4.69 秒。各块的帧数、画面内容和初始化开销均可能影响时间。LaMa 引导模型只加载一次，用时 2.60 秒。

早期快速档的三条同片对照覆盖普通英文、粗描边和双语底板。原 CLEAR 快速在 c01、c06、c11 分别用时 56.27、60.94、62.82 秒。初始 PP-OCRv5 Mobile＋LaMa 分别为 35.58、26.35、39.18 秒。三条合计为 180.02 秒和 101.11 秒。此处比较的是快速档候选，正式档位速度按全部 15 条的总用时另行核算。

### 字幕与水印的混合样片

x01 同时带彩色解说字幕和右下角三行平台水印。在第一轮配置中，人物解说的“6.3 亿美元”切镜时连续两帧完整保留，后续仍可读出“亿美元”。原有笔画检测偏向白色和黄色，粉色后缀的部分像素落在修复遮罩外。引导图沿用原字幕，最终合成时又把漏选像素保留下来。自动逐帧 OCR 对这段 120 帧原片仅有 1 帧给出文字结果，人工逐帧并排检查发现了这个问题。

在调参素材上补充了深色画面中的同色、同基线文字检测。连续几帧有清晰文字时，也检查相邻帧的弱对比淡入字形。冻结后的 Pro 和 Max 都擦除了切镜淡入和尾帧的彩色文字。Pro 共 113.98 秒，任务峰值 10,378 MiB，整卡平均利用率 46.6%。Max 共 124.35 秒，峰值 10,456 MiB，利用率 51.6%。两档均先调用 CLEAR、再调用 ProPainter。Max 另复查 120 帧水印，选出的二次精修区间为零。右下三行标记已经消失。把两条路线的成片放回原尺寸比较，第 0 至 2 帧原首字“已”的位置仍有对应字形，随后变成亮块。该处按残字记入，水印区局部变软。按本次交付标准，这条混合样片两档均记为画质未通过。

## 混合样片的另一条实测路径

在调参片 x01 上先单独运行冻结 Lite 的 OCR＋LaMa 去字幕，再对前一步成片使用冻结 Pro 的水印参数单独运行 ProPainter。两段各自导出，耗时 24.73 秒和 39.63 秒，处理合计 64.36 秒，运行程序的墙钟耗时 67.03 秒。两个阶段采样到的单任务峰值显存分别为 0.84 和 5.35 GiB。

在所选区域中，“已经狂卖了645万份”、淡入的粉色“6.3亿美元”和右下三行水印均已去除。第 0 至 2 帧没有冻结 Pro 和 Max 留下的“已”字形或随后出现的白块。右下暗部、切镜后地面的细纹稍软，全画面对照和尾帧未见突出的色块，本片画质通过。该结果来自一条 4 秒调参样片。已作为实验路线留存，Web 和 PHP 仍使用本轮冻结的三档。[混合样片分段结果](../benchmarks/l20/results/20261127/mixed-pilot.json)

## 复现

`benchmarks/l20/run_candidate.py` 运行隔离的单任务试验，保留输入摘要、实际参数、分帧校验、推理阶段和资源采样。`run_acceptance.py` 核查冻结版本后执行主清单和并发组合。`check_live_entries.py` 对同一输入实际发送两次 HTTP 请求，核对提交来源、计划、执行程序摘要及下载文件。并发记录中的 GPU 重叠时间指两个任务的模型调用时间区间有交集，整批耗时衡量吞吐收益。[调度和计时口径](queue-scheduling.md)

并发批次中的每份独立成片按文件摘要登记。与单任务成片的文件或全部解码画面相同，可以复用已完成的画质判定。画面不同的输出用本批实际成片与原片对照，单独登记。调度器报告的 GPU 利用率来自整张卡，任务显存按进程归属。持续时间很短的阶段可能恰好没有采样点，逐阶段表中保留空值。

复核数据包含[硬件与权重摘要](../benchmarks/l20/results/20261127/machine.json)、[绑定成片摘要的逐片意见](../benchmarks/l20/results/20261127/quality-reviews.json)、[客户端上传时间](../benchmarks/l20/results/20261127/client-upload.csv)与[整轮结构化结果](../benchmarks/l20/results/20261127/summary.json)。同一份模型配置和单任务基线可按冻结版本重跑。私有样片和可播放的左右对比视频交付在操作者本机。
