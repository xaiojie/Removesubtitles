# L20 快速档完整片段测试

本轮在同一张 L20 上比较 PP-OCRv5 Mobile＋Big-LaMa 和原 CLEAR 快速。21 条主测覆盖普通字、粗描边和带底板字幕，另外记录黄底片尾回归和带干净参考的样片。每次推理使用清单中的完整片段，每条最长 30 秒。干净原片与官方遮罩只用于成片评估。

## OCR 在 GPU 上执行

从当前 Paddle 检测器导出 FP32 ONNX，在同一份 PaddleX 图像预处理、阈值和轮廓提取流程中替换模型计算。7 个来源的 40 个选区抽样得到相同的检测多边形。单次检测中位数从 87.83 毫秒降至 10.73 毫秒。运行轨迹中记录到的 11,200 个计算节点均由 CUDA 执行。

在相同底板跟踪、推理尺寸和 LaMa 参数下，只切换 OCR 执行器，P01 的完整耗时由 92.467 秒降到 74.115 秒，N01 由 55.688 秒降到 47.690 秒。两条均核对了整份 MP4，CPU 版和 GPU 版的 SHA-256 分别相同。P01 对照中同一段 198 帧的麦克风标志均得以保留。原快速档在该段只保留了 8 帧。

以下指令适用于本轮使用的 Linux x86-64、Python 3.11 和 CUDA 12 环境，在仓库根目录执行。

```bash
video-subtitle-remover/.venv/bin/python -m pip install \
  "onnxruntime-gpu==1.22.0" "paddle2onnx==2.1.0" "onnx==1.17.0"
video-subtitle-remover/.venv/bin/python scripts/export_lite_ocr.py \
  video-subtitle-remover/backend/models/V5/ch_det_fast
```

导出工具校验本地源权重和 ONNX 文件。相同输入、工具版本及有效输出可直接复用。本轮使用的导出图 SHA-256 为 `c8d9b07063420ce5365c74e42532de48238feeeedcdb7a330b195708bc38a93f`。运行器通过 `ocr_backend=onnx_cuda` 选择 GPU 定位，并在执行记录中写入实际加载的摘要。Big-LaMa 继续使用原始权重。

### 同卡两条视频并发

使用第二版测试站的实际任务调度器，提交 U02 游戏对白与 P04 绿色逐词字幕，各 900 帧。两个视频串行共 103.31 秒，并发共 62.57 秒。并发调用 OCR 或 LaMa 的时间重叠 12.21 秒，整卡最高显存从 3,784 MiB 增至 5,286 MiB，采样最高 GPU 利用率从 65% 增至 96%。两次均完成 2 个任务，两条成片各自的串行和并发摘要一致。按成功编码数量折算，吞吐从 34.85 增至 57.54 分钟素材/小时。成片的画质另行验收，P04 胸牌被字覆盖的位置仍会变软。

第三版在同一台 L20 上重复了这组调度测试。两个视频串行用时 92.83 秒，并发用时 58.29 秒。GPU 模型调用重叠 13.13 秒，整卡峰值显存分别为 3,784 和 5,286 MiB，GPU 利用率峰值分别为 67% 和 93%。两组均完成两条，各条在两种调度方式下下载的文件摘要相同。按完整编码的素材时长计算，吞吐分别为每小时 38.78 和 61.77 分钟。第三版测试站也从 Web 和 PHP API 分别提交了完整 U03，成片摘要一致，耗时分别为 56.09 和 54.29 秒。

### 窄字幕带和静止背景

工程机械教程 N03 长 30 秒，共 750 帧。22.36～24.72 秒的两行字挡在螺栓和支架上。按原字幕每行至少四分之一亮笔画仍可见计，第四版在各有 59 帧可测的两行中分别漏了 6 帧和 52 帧。在窄选区提高 OCR 输入分辨率，两行各降至 0 帧，螺栓却被 LaMa 抹去一部分。再使用本镜头已经露出过的背景，螺栓的边缘匹配率从 32.8% 升到 95.6%。三份成片分别耗时 30.970、31.087 和 31.109 秒。

### 每句底板高度变化和两个不同形状的选区

熊蜂实验片 P06 的灰底跟着字幕改变宽度，下边缘也会随句子上下移动约 5 个像素。第四版要求下边缘固定，最后放弃了已经检测到的底板。候选参数 `alternate_line_heights` 用原片中反复出现的两种高度校准，再按当前帧的边缘恢复底色。完整 30 秒从 44.639 秒降到 35.704 秒。677 个能量出原底板上下边缘的帧中，成片明显保留两条边的帧数由 379 降到 15。0.47 秒和 27.33 秒仍有灰底，10.70 秒的背景大字也有损伤。

R01 全长 27.37 秒，包含一条竖选区和一条横选区。两个不同形状的输入轮流进入同一个 OCR 执行器时，816 次 GPU 检测合计用去 53.73 秒。候选参数 `split_ocr_shapes` 给第二种输入尺寸单独分配执行器，保留相同的权重和检测参数。GPU 检测降至 3.62 秒，完整处理由 117.935 秒降至 70.107 秒，峰值显存从 3,090 增至 3,144 MiB。两份成片含 821 帧，整份文件的 SHA-256 相同。

第四版测试站处理 U02 和 P04 时，串行共 77.06 秒，并发共 48.79 秒，两个视频的 GPU 模型调用重叠 3.11 秒。两次都成功编码两条，逐片的串行和并发下载文件相同。整卡峰值显存分别为 3,952 和 5,582 MiB。Web 与 PHP API 各提交的 U03 成片摘要也一致。[完整单片耗时、像素判定和服务对照](../benchmarks/l20/results/20261127-round2/lite-panels-and-multiroi.json)

### 快速档第五版的验收配置
